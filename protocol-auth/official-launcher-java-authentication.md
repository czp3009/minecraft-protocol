# Official Minecraft Launcher Java Edition Authentication Flow

This document describes the authentication performed by the Microsoft Store version of Minecraft Launcher on Windows
before it starts a Minecraft: Java Edition client.

The flow ends after the Java command line has been materialized. It does not include the protocol used by the running
game to join a multiplayer server.

| Microsoft Store product ID                   | `9PGW18NPBZV5`                                           |

`00000000402B5328` is the fixed Microsoft OAuth `client_id`. The `--clientId` value later passed to Java is a different
identifier: it is an installation-scoped UUID obtained from Windows and persisted by the launcher.

Every HTTP exchange below shows the successful response used by the launcher. Response headers are shown when the
launcher consumes them or when they identify the body representation. Token-producing steps show the network path taken
on a cache miss or required refresh; a still-valid cached token satisfies the same step without an HTTP exchange and has
the same downstream consumers. An angle-bracket value in a request is either labeled with its producing step or defined
immediately beside that request. An angle-bracket value in a response is generated by that server; the text after the
response states whether it is consumed later or is only response metadata.

## Credential chain

The launcher obtains and uses these distinct credentials:

1. A Microsoft OAuth access token and refresh token.
2. An Xbox device token.
3. An Xbox user token and title token.
4. An XSTS token whose audience is `rp://api.minecraftservices.com/`.
5. A Minecraft Services access token.
6. A Microsoft Store User Collections ID JWT and license JWT.

Only the Minecraft Services access token is passed to Java as `--accessToken`. The preceding credentials are inputs to
the token exchanges that produce it. The Store JWTs are used to prove product ownership.

The successful flow is:

```text
device identity
  -> Xbox device token
  -> Microsoft OAuth token
  -> Xbox user and title tokens
  -> Minecraft-services XSTS token
  -> Minecraft Services access token
  -> Store entitlement verification
  -> Java profile
  -> Java command-line arguments
```

## 1. Establish the device identity and request-signing key

The launcher uses a persistent device GUID and a persistent P-256 key pair as the Windows device identity. The public
key is represented as a JSON Web Key:

```json
{
  "kty": "EC",
  "alg": "ES256",
  "crv": "P-256",
  "x": "<base64url-encoded public-key X coordinate>",
  "y": "<base64url-encoded public-key Y coordinate>",
  "use": "sig"
}
```

When the cached Xbox endpoint-signing policy is absent or stale, the launcher first requests the current policy:

```http
GET https://title.mgt.xboxlive.com/titles/default/endpoints?type=1
```

The `GET` has no request body.

The successful response header consumed for request correlation is:

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
MS-CV: <server correlation vector>
```

The response body is JSON. The arrays below are abbreviated because the service returns a catalog covering many Xbox
hosts; this shows the complete top-level shape and the entries that govern the requests in this flow:

```json
{
  "EndPoints": [
    {
      "Protocol": "https",
      "Host": "sisu.xboxlive.com",
      "HostType": "fqdn",
      "RelyingParty": "http://sisu.xboxlive.com/",
      "TokenType": "JWT",
      "SignaturePolicyIndex": 0
    }
  ],
  "SignaturePolicies": [
    {
      "Version": 1,
      "SupportedAlgorithms": [
        "ES256"
      ],
      "MaxBodyBytes": 8192,
      "SupportedSignatureTypes": [
        "XBL"
      ]
    }
  ],
  "Certs": [
    {
      "Thumbprint": "<certificate thumbprint>",
      "IsIssuer": true,
      "RootCertIndex": 0
    }
  ],
  "RootCerts": [
    "<base64-encoded DER root certificate>"
  ]
}
```

Each complete `EndPoints` entry maps a protocol, host type, host, and optional path to a relying party, token type,
optional server-certificate indices, and optional `SignaturePolicyIndex`. That index selects an entry from
`SignaturePolicies`. The service body also contains `Certs` and `RootCerts`; the authentication path described here
selects endpoints and request-signing rules from `EndPoints` and `SignaturePolicies`. All catalog values are
service-generated policy data; none is supplied by a preceding authentication step.

The launcher generates a correlation vector for a new operation and advances it from `MS-CV` response headers. It
applies the matching signature policy to protected Xbox requests and sends the resulting `Signature` and `MS-CV`
headers. Versioned Xbox JSON endpoints also receive:

```http
x-xbl-contract-version: 1
```

The signature binds the HTTP method, request path, timestamp, proof key, and body to the persistent device private key.
Every request described below as signed uses this identity. `MS-CV` is operation-correlation data generated and advanced
by the launcher; it is not an authentication token.

## 2. Obtain the Xbox device token

The launcher first checks its device-token cache. If no unexpired token is available, it sends a signed request:

```http
POST https://device.auth.xboxlive.com/device/authenticate
Content-Type: application/json; charset=utf-8
x-xbl-contract-version: 1
MS-CV: <correlation vector generated and advanced as described in step 1>
Signature: <ES256 request signature made with the device key from step 1>
```

The request body is:

```json
{
  "RelyingParty": "http://auth.xboxlive.com",
  "TokenType": "JWT",
  "Properties": {
    "AuthMethod": "ProofOfPossession",
    "Id": "<persistent device GUID>",
    "DeviceType": "Win32",
    "Version": "<Windows version>",
    "SerialNumber": "<device serial identifier>",
    "DeviceModel": "<device model>",
    "DeviceSku": "<device SKU>",
    "ProofKey": {
      "kty": "EC",
      "alg": "ES256",
      "crv": "P-256",
      "x": "<base64url-encoded public-key X coordinate from step 1>",
      "y": "<base64url-encoded public-key Y coordinate from step 1>",
      "use": "sig"
    }
  }
}
```

`Version`, `SerialNumber`, `DeviceModel`, and `DeviceSku` are included when Windows supplies the corresponding values.

The successful response headers identify a JSON body:

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
MS-CV: <updated correlation vector>
```

The response body has this structure:

```json
{
  "IssueInstant": "<issue time>",
  "NotAfter": "<expiry time>",
  "Token": "<Xbox device token>",
  "DisplayClaims": {
    "xdi": [
      {
        "<device claim>": "<value>"
      }
    ]
  }
}
```

`IssueInstant` and `NotAfter` are the device token's server-generated validity bounds. The launcher caches `Token` until
`NotAfter` and passes it as `DeviceToken` during interactive sign-in and Xbox authorization. Step 4 returns the device
token value that step 5 uses for XSTS authorization. `DisplayClaims.xdi` is device-claim metadata carried with the
response; it is not an input to a later request in this flow.

## 3. Obtain a Microsoft OAuth token

For a previously authenticated account, the launcher first asks for a Microsoft access token for the fixed scope. A
still-current access token in the persisted ticket set satisfies that request without an HTTP exchange. Otherwise, the
launcher silently uses the stored refresh token. If neither cached credential can satisfy the request, or if Microsoft
requires user interaction, the launcher performs an authorization-code flow with PKCE in its embedded Chromium browser.

### 3.1 Silent refresh

The stored refresh token is the `refresh_token` returned by an earlier successful step 3.1 or step 3.5. When refresh is
required, the launcher submits:

```http
POST https://login.live.com/oauth20_token.srf
Content-Type: application/x-www-form-urlencoded; charset=utf-8

client_id=00000000402B5328&
grant_type=refresh_token&
refresh_token=<stored Microsoft refresh token>&
scope=service%3A%3Auser.auth.xboxlive.com%3A%3AMBI_SSL
```

The line breaks above are for presentation; the actual body is one form-encoded payload. The successful response headers
identify a JSON body:

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
```

The response body contains:

```json
{
  "token_type": "<token type>",
  "expires_in": <lifetime
  in
  seconds>,
  "scope": "service::user.auth.xboxlive.com::MBI_SSL",
  "access_token": "<new Microsoft OAuth access token>",
  "refresh_token": "<new Microsoft OAuth refresh token>"
}
```

The launcher replaces the stored refresh token with the returned `refresh_token`, stores `access_token` for the returned
`scope`, and computes its expiry from `expires_in`. `token_type` describes how that access token is presented; it is not
forwarded as a separate value. The launcher then continues at step 4 with the returned `access_token`.

The launcher is registered as a public native client. Neither this refresh request nor the authorization-code exchange
sends a `client_secret` field.

### 3.2 Create the PKCE and state values

For interactive sign-in, the launcher generates:

- a one-use, high-entropy `code_verifier`;
- `BASE64URL(SHA-256(code_verifier))` without padding as `code_challenge`;
- a one-use random `state` value.

The `code_verifier` remains inside the launcher. The `code_challenge` and `state` are sent to the interactive sign-in
endpoint.

### 3.3 Initialize interactive sign-in

The launcher sends a signed request:

```http
POST https://sisu.xboxlive.com/authenticate
Content-Type: application/json; charset=utf-8
MS-CV: <correlation vector generated and advanced as described in step 1>
Signature: <ES256 request signature made with the device key from step 1>
```

The request body is:

```json
{
  "AppId": "00000000402B5328",
  "TitleId": "1794566092",
  "RedirectUri": "https://login.live.com/oauth20_desktop.srf",
  "DeviceToken": "<device token from step 2>",
  "Sandbox": "RETAIL",
  "TokenType": "code",
  "Offers": [
    "service::user.auth.xboxlive.com::MBI_SSL"
  ],
  "Query": {
    "display": "<Windows sign-in display mode>",
    "code_challenge": "<PKCE code_challenge from step 3.2>",
    "code_challenge_method": "S256",
    "state": "<random state from step 3.2>",
    "prompt": "select_account"
  }
}
```

`display` is omitted when Windows does not supply a display-mode value. All other dynamic request fields identify their
producing step inline.

The successful response headers are:

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
X-SessionId: <SISU session ID>
X-Cluster-Affinity: <HTTPS SISU cluster base URL>
MS-CV: <updated correlation vector>
```

The response body is:

```json
{
  "MsaOauthRedirect": "<browser start URL>",
  "MsaRequestParameters": {
    "<parameter name>": "<parameter value>"
  }
}
```

`MsaOauthRedirect` is the start URL consumed by step 3.4. Every service-generated string member of
`MsaRequestParameters` is handed to the embedded-browser operation for the same sign-in session; the launcher does not
synthesize those values. `X-SessionId` becomes the `SessionId` body field in step 4. The launcher validates that
`X-Cluster-Affinity` is HTTPS and uses it as the authorization base URL in step 4; if the header is absent, it uses the
default `https://sisu.xboxlive.com` base.

### 3.4 Complete Microsoft sign-in in the embedded browser

The launcher creates an embedded Chromium browser and performs the following navigation inside it:

```http
GET <MsaOauthRedirect returned by step 3.3>
```

When the interactive operation retains an existing Microsoft refresh token, the browser host adds these headers to the
initial navigation:

```http
x-ms-sso-RefreshToken: <stored refresh token from an earlier step 3.1 or 3.5>
x-ms-sso-Ignore-SSO: 1
```

Those headers are absent when no refresh token is available. The initial `GET` has no request body. This is a browser
navigation rather than a launcher-owned JSON exchange. The navigation receives Microsoft HTML documents with
`Content-Type: text/html` and follows any `3xx` responses through their `Location` headers. Microsoft owns the rendered
bodies and the browser-generated form requests for account selection, credentials, passwordless authentication,
multifactor authentication, and consent.

After successful sign-in, a Microsoft response redirects the browser to the registered final URL:

```http
HTTP/1.1 302 Found
Location: https://login.live.com/oauth20_desktop.srf?code=<authorization code>&state=<state from step 3.2>&...
```

The response body accompanying that redirect is not consumed. The resulting navigation target is:

```text
https://login.live.com/oauth20_desktop.srf?code=<authorization code>&state=<state from step 3.2>&...
```

This is an HTTPS desktop redirect URI, not a custom URI that launches the application. The browser host is given both a
start URL and a final URL. It recognizes the redirect to the final URL, returns the complete redirected URL directly to
the launcher process, and closes the sign-in page. No loopback HTTP listener is created.

The launcher checks the returned `state` against the value from step 3.2 and extracts `code` only after that check
succeeds. Additional query parameters represented by `...` remain part of the returned URL but are not inputs to later
requests. The launcher does not consume a body from the final desktop redirect page.

### 3.5 Exchange the authorization code

The launcher submits:

```http
POST https://login.live.com/oauth20_token.srf
Content-Type: application/x-www-form-urlencoded; charset=utf-8

grant_type=authorization_code&
code=<authorization code from step 3.4>&
client_id=00000000402B5328&
redirect_uri=https%3A%2F%2Flogin.live.com%2Foauth20_desktop.srf&
code_verifier=<PKCE code_verifier from step 3.2>&
scope=service%3A%3Auser.auth.xboxlive.com%3A%3AMBI_SSL
```

The successful response headers identify a JSON body:

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
```

The response body contains:

```json
{
  "token_type": "<token type>",
  "expires_in": <lifetime
  in
  seconds>,
  "scope": "service::user.auth.xboxlive.com::MBI_SSL",
  "access_token": "<Microsoft OAuth access token>",
  "refresh_token": "<Microsoft OAuth refresh token>"
}
```

The launcher persists `refresh_token`, stores `access_token` for the returned `scope`, and computes its expiry from
`expires_in`. `token_type` is response metadata and is not forwarded separately. Both the silent and interactive
branches therefore provide step 4 with a current Microsoft OAuth `access_token`.

## 4. Obtain the Xbox user and title tokens

For the interactive branch, `authorizeBase` is the validated `X-Cluster-Affinity` value returned by step 3.3. If that
header was absent, and for the silent branch, `authorizeBase` is the configured default `https://sisu.xboxlive.com`.

If the required Xbox user and title tokens are not already valid in the token cache, the launcher sends a signed
request:

```http
POST <authorizeBase defined above>/authorize
Content-Type: application/json; charset=utf-8
MS-CV: <correlation vector generated and advanced as described in step 1>
Signature: <ES256 request signature made with the device key from step 1>
```

For the interactive branch, the request body is:

```json
{
  "AccessToken": "t=<Microsoft OAuth access token from step 3>",
  "AppId": "00000000402B5328",
  "DeviceToken": "<device token from step 2>",
  "Sandbox": "RETAIL",
  "UseModernGamertag": true,
  "SiteName": "user.auth.xboxlive.com",
  "RelyingParty": "http://xboxlive.com",
  "SessionId": "<X-SessionId from step 3.3>",
  "ProofKey": {
    "kty": "EC",
    "alg": "ES256",
    "crv": "P-256",
    "x": "<base64url-encoded public-key X coordinate from step 1>",
    "y": "<base64url-encoded public-key Y coordinate from step 1>",
    "use": "sig"
  }
}
```

The silent branch has no newly created `X-SessionId` and omits `SessionId`. All other listed values have the same
source.

The successful response headers are:

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
X-SessionId: <current SISU session ID>
X-Cluster-Affinity: <current HTTPS SISU cluster base URL>
MS-CV: <updated correlation vector>
```

The launcher retains the two SISU headers when present so that a continuation or retry remains in the same session and
cluster. They are not inputs to step 5.

The response body contains:

```json
{
  "DeviceToken": "<updated device token>",
  "TitleToken": {
    "IssueInstant": "<issue time>",
    "NotAfter": "<expiry time>",
    "Token": "<Xbox title token>",
    "DisplayClaims": {
      "xti": [
        {
          "<title claim>": "<value>"
        }
      ]
    }
  },
  "UserToken": {
    "IssueInstant": "<issue time>",
    "NotAfter": "<expiry time>",
    "Token": "<Xbox user token>",
    "DisplayClaims": {
      "xui": [
        {
          "<user claim>": "<value>"
        }
      ]
    }
  },
  "AuthorizationToken": {
    "IssueInstant": "<issue time>",
    "NotAfter": "<expiry time>",
    "Token": "<authorization token for http://xboxlive.com>",
    "DisplayClaims": {
      "xui": [
        {
          "<user claim>": "<value>"
        }
      ]
    }
  },
  "Sandbox": "RETAIL",
  "UseModernGamertag": true
}
```

Step 5 consumes `DeviceToken`, `TitleToken.Token`, and `UserToken.Token`. Each token object's `IssueInstant` and
`NotAfter` are its cache-validity bounds. The title and user `DisplayClaims` objects carry service-generated identity
metadata; in particular, the user token's `xui` claim supplies the signed-in Xbox user identity. `AuthorizationToken`
has `http://xboxlive.com` as its relying party and is not sent directly to Minecraft Services. The returned `Sandbox`
and `UseModernGamertag` values describe the completed authorization and do not become separate inputs to step 5.

## 5. Obtain an XSTS token for Minecraft Services

If no valid XSTS token exists for the exact Minecraft Services relying party, device, title, user, and sandbox
combination, the launcher sends a signed request:

```http
POST https://xsts.auth.xboxlive.com/xsts/authorize
Content-Type: application/json; charset=utf-8
x-xbl-contract-version: 1
MS-CV: <correlation vector generated and advanced as described in step 1>
Signature: <ES256 request signature made with the device key from step 1>
```

The request body is:

```json
{
  "RelyingParty": "rp://api.minecraftservices.com/",
  "TokenType": "JWT",
  "Properties": {
    "SandboxId": "RETAIL",
    "DeviceToken": "<DeviceToken returned by step 4>",
    "TitleToken": "<TitleToken.Token from step 4>",
    "UserTokens": [
      "<UserToken.Token from step 4>"
    ]
  },
  "OptionalDisplayClaims": [
    "mgt",
    "mgs",
    "umg"
  ]
}
```

The optional display-claim names request the modern gamertag, modern gamertag suffix, and unique modern gamertag values
for the signed-in user.

The successful response headers identify a JSON body:

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
MS-CV: <updated correlation vector>
```

The response body contains:

```json
{
  "IssueInstant": "<issue time>",
  "NotAfter": "<expiry time>",
  "Token": "<XSTS token for Minecraft Services>",
  "DisplayClaims": {
    "xui": [
      {
        "uhs": "<Xbox user hash>",
        "xid": "<Xbox user ID>",
        "gtg": "<gamertag>",
        "mgt": "<modern gamertag>",
        "mgs": "<modern gamertag suffix>",
        "umg": "<unique modern gamertag>"
      }
    ]
  }
}
```

`IssueInstant` and `NotAfter` are the XSTS token's server-generated validity bounds. The requested modern-gamertag
members are returned when they apply to the account. The launcher takes `DisplayClaims.xui[0].uhs` and `Token` and
constructs:

```text
XBL3.0 x=<uhs from this response>;<Token from this response>
```

That complete string becomes `xtoken` in step 6. The launcher retains `DisplayClaims.xui[0].xid` as the Xbox user ID for
the Java `--xuid` argument. The gamertag fields are account-display metadata and are not inputs to step 6.

## 6. Obtain the Minecraft Services access token

When the launcher needs a new Minecraft Services access token, it sends:

```http
POST https://api.minecraftservices.com/launcher/login
Content-Type: application/json
```

The request body is:

```json
{
  "platform": "ONESTORE",
  "xtoken": "XBL3.0 x=<uhs from step 5>;<XSTS Token from step 5>"
}
```

The successful response headers identify a JSON body:

```http
HTTP/1.1 200 OK
Content-Type: application/json
```

The response body has these top-level fields:

```json
{
  "username": "<Minecraft Services account identifier>",
  "roles": [
    "<account role>"
  ],
  "access_token": "<Minecraft Services access token>",
  "token_type": "Bearer",
  "expires_in": <lifetime
  in
  seconds>,
  "launcher_data": {
    "azure_access_token": "<Microsoft Store collections service ticket>",
    "license_data": {
      "request_id": "<license request ID>",
      "products_ids": [
        "<Microsoft Store product ID>"
      ]
    }
  },
  "metadata": {
    "pending_removal": {
      "at": "<scheduled account-removal time>"
    }
  }
}
```

`launcher_data`, `metadata`, and their members are optional in the response. When present, `license_data.request_id` is
a UUID-form request identifier and `license_data.products_ids` is the product-ID list for the Store license query. The
launcher defines `entitlementRequestId` as that returned `request_id`, or as a newly generated GUID when the field is
absent. `metadata.pending_removal.at` carries a scheduled account-removal time for account-state handling.

The launcher stores `access_token` and computes its expiry from `expires_in`; `token_type` identifies it as a bearer
token. This token authenticates the following Minecraft Services calls and later becomes Java's `--accessToken`. The
launcher retains `username` as the remote account identifier and supplies it as `publisherUserId` in step 7. `roles` is
account-role metadata and is not an input to a later request. `launcher_data` is used only for the product-ownership
check in step 7 and is not passed to Java.

## 7. Verify Microsoft Store product ownership

The launcher creates a Microsoft Store context for the Windows user currently signed in to Microsoft Store. That Store
user is supplied by Windows and is not derived from an earlier token in this flow. The package's fixed Store product ID
is `9PGW18NPBZV5`; the product list returned in `launcher_data.license_data.products_ids` determines the IDs submitted
for this account. When step 6 returns the corresponding `launcher_data`, the launcher starts two Store operations:

1. It calls `XStoreGetUserCollectionsIdAsync` with `launcher_data.azure_access_token` from step 6 as `serviceTicket` and
   `username` from step 6 as `publisherUserId`. After completion, `XStoreGetUserCollectionsIdResult` returns an opaque
   User Collections ID JWT; the launcher names that value `userStoreAuthJwt`.
2. It calls `XStoreQueryLicenseTokenAsync` with `launcher_data.license_data.products_ids` from step 6 as the product
   list. The custom developer string round-tripped inside the license token is
   `{"CampaignId":"MinecraftLauncher","OptionalCampaignId":"MinecraftLauncher"}`. After completion,
   `XStoreQueryLicenseTokenResult` returns an opaque license JWT; the launcher names that value `licenseJwt`.

These are Windows Store API operations. Their transport-level HTTP response headers and bodies are not exposed to the
launcher. Each asynchronous operation returns an `HRESULT`; its result function returns one null-terminated opaque token
string. `launcher_data.license_data.request_id` does not enter either Store JWT. Step 6 has already copied it, or a
generated replacement, into `entitlementRequestId`.

The normal entitlement request is:

```http
POST https://api.minecraftservices.com/entitlements/license?requestId=<entitlementRequestId from step 6>
Authorization: Bearer <Minecraft Services access token from step 6>
Content-Type: application/json
```

Its body is:

```json
{
  "licenseJwt": "<licenseJwt returned by the Store operation above>",
  "userStoreAuthJwt": "<userStoreAuthJwt returned by the Store operation above>"
}
```

When both Store JWTs are absent, the launcher uses the compatibility request instead:

```http
GET https://api.minecraftservices.com/entitlements/license?requestId=<entitlementRequestId from step 6>
Authorization: Bearer <Minecraft Services access token from step 6>
```

The compatibility `GET` has no request body.

Both request forms have the same successful response headers:

```http
HTTP/1.1 200 OK
Content-Type: application/json
```

The response body contains:

```json
{
  "items": [
    {
      "name": "game_minecraft",
      "signature": "<item signature>"
    }
  ],
  "signature": "<response signature>",
  "keyId": "<signing-key ID>",
  "requestId": "<entitlementRequestId echoed by the service>"
}
```

The launcher requires returned `requestId` to match `entitlementRequestId` and uses `keyId` to select an embedded
entitlement public key. It verifies the top-level `signature` and every item `signature`, then maps each signed item
`name`, including `game_minecraft`, to the account's Java Edition entitlement. These response fields do not become
inputs to another HTTP request; the verified result determines whether the launcher may prepare a full Java Edition
launch or must prepare a restricted launch.

## 8. Retrieve the Java Edition profile

After entitlement processing, the launcher sends:

```http
GET https://api.minecraftservices.com/minecraft/profile
Authorization: Bearer <Minecraft Services access token from step 6>
```

The `GET` has no request body. The successful response headers are:

```http
HTTP/1.1 200 OK
Content-Type: application/json
```

The response body has this structure:

```json
{
  "id": "<Minecraft UUID without hyphens>",
  "name": "<Java Edition player name>",
  "skins": [
    {
      "id": "<skin ID>",
      "state": "<skin state>",
      "url": "<texture URL>",
      "variant": "<CLASSIC or SLIM>",
      "alias": "<skin alias>"
    }
  ],
  "capes": [
    {
      "id": "<cape ID>",
      "state": "<cape state>",
      "url": "<texture URL>",
      "alias": "<cape alias>"
    }
  ],
  "profileActions": []
}
```

The launcher uses `id` and `name` for the Java command line. Every field inside `skins` and `capes`, and each value in
`profileActions`, is server-generated profile metadata used for profile display and account-state handling; none is an
input to a later authentication request.

## 9. Materialize the Java command line

Before each launch, the launcher ensures that the Minecraft Services access token is current. If the stored token is no
longer valid for the launch, it resumes at step 3, uses a cached Microsoft token or refresh token as available, and
repeats the downstream token exchanges. It never passes the Microsoft refresh token, Xbox tokens, XSTS token, or Store
JWTs to Java.

The selected Minecraft: Java Edition version metadata defines these authentication-related arguments:

```text
--username ${auth_player_name}
--uuid ${auth_uuid}
--accessToken ${auth_access_token}
--clientId ${clientid}
--xuid ${auth_xuid}
```

The launcher resolves them as follows:

| Placeholder            | Value                                              |
|------------------------|----------------------------------------------------|
| `${auth_player_name}`  | `name` from the Java profile in step 8             |
| `${auth_uuid}`         | `id` from the Java profile in step 8               |
| `${auth_access_token}` | Minecraft Services `access_token` from step 6      |
| `${auth_xuid}`         | `DisplayClaims.xui[0].xid` from step 5             |
| `${clientid}`          | UUID persisted for the local launcher installation |

The install-scoped client ID is stored in `clientId_v2.txt` as a standard 36-character UUID. If the launcher cannot
obtain the value from Windows, it generates and persists a random UUID instead. This value is not the OAuth application
ID `00000000402B5328`.

The Java command line carries neither the Minecraft Services token's expiry nor any refresh credential. It carries only
the current bearer token value.

The complete set of ordinary game arguments also contains the selected version and local installation paths:

```text
--username ${auth_player_name}
--version ${version_name}
--gameDir ${game_directory}
--assetsDir ${assets_root}
--assetIndex ${assets_index_name}
--uuid ${auth_uuid}
--accessToken ${auth_access_token}
--clientId ${clientid}
--xuid ${auth_xuid}
--versionType ${version_type}
```

The remaining placeholders are resolved from the selected installation rather than from authentication responses:

| Placeholder            | Value                                                         |
|------------------------|---------------------------------------------------------------|
| `${version_name}`      | ID of the selected Java version                               |
| `${game_directory}`    | resolved game directory of the selected launcher installation |
| `${assets_root}`       | resolved local assets directory                               |
| `${assets_index_name}` | asset-index ID named by the selected version metadata         |
| `${version_type}`      | `type` value from the selected version metadata               |

At this point the launcher has a verified Java Edition entitlement, a Java profile, an Xbox user ID, and a current
Minecraft Services access token, and the Java process arguments are fully materialized.
